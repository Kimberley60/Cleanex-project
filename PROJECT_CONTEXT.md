# CLEANEX Project Context

## Project overview and purpose

CLEANEX is a professional cleaning-services web application for the Kenyan market. It lets guests and registered customers request quotes, book cleaning services, track bookings, and pay by M-Pesa, while staff manage services, bookings, quotes, notifications, and CMS content through Django admin.

## Technology stack and development environment

- Django (Python) with class-based and function-based views.
- PostgreSQL locally and Neon PostgreSQL for deployment; `DATABASE_URL` is supported for hosted providers.
- Bootstrap 5 plus custom CSS/JavaScript in `static/` and `templates/`.
- Environment configuration uses `python-decouple` (`from decouple import config, Csv`); secrets are never committed.
- Cloudinary for uploaded media when `CLOUDINARY_*` credentials are configured; local `FileSystemStorage` is the fallback.
- WhiteNoise serves collected static files in production; Gunicorn is the production WSGI server.
- Local development uses the project virtualenv at `.venv` (e.g., `.\.venv\Scripts\python.exe manage.py ...`).

## Current directory and application structure

- `config/` — project settings and root URLconf.
- `cleanexapp/` — minimal project app (placeholder tests).
- `apps_core/` — all feature apps:
  - `core/` — home/contact pages, CMS models, contact email, public rate limiting.
  - `customers/` — customer accounts, registration/verification, profile, dashboard.
  - `services/` — service categories, services, features, FAQs, extras.
  - `staff/` — staff records and availability/assignment services.
  - `bookings/` — booking model/services/views, tracking, admin.
  - `quotes/` — quote requests, pricing estimates, staff quotation workflow.
  - `payments/` — payment model/services, M-Pesa Daraja integration, callback, reconciliation command.
  - `notifications/` — quote-status notification persistence/delivery/retry.
  - `gallery/` — legacy gallery and public `GalleryPhoto` records.
  - `website/` — hero/process CMS models and the shared `website_content` context processor.
- `templates/` — `base/`, `components/`, `includes/`, `pages/`, `accounts/`, `emails/`, `errors/`, `registration/`, `services/`.
- `static/` — CSS/JS assets; `staticfiles/` is generated by `collectstatic` and ignored by Git.
- `media/` — local uploaded files in development; ignored by Git and replaced by Cloudinary when configured.

## Architecture: Data → Business Logic → UI

- **Data:** Django models in each app's `models.py`; relationships are enforced with `PROTECT`/`SET_NULL`/`CASCADE` as appropriate.
- **Business logic:** service-layer functions in each app's `services.py` (e.g., `create_booking`, `change_booking_status`, `create_quote_request`, `change_quote_status`, `create_payment`, `verify_payment`, `deliver_quote_status_notification`). Views stay thin and delegate to services.
- **UI:** Django templates with inheritance (`templates/base/base.html`), reusable components, and Bootstrap styling. Public pages are served by class-based/function views; staff workflows live in Django admin.

## Application responsibilities

- **customers:** `Customer` and `PendingCustomerRegistration` models; registration, email verification, login/logout, password reset, profile, dashboard, quote history. Normalized-email uniqueness is enforced at the DB level.
- **quotes:** `QuoteRequest` model; guest and authenticated quote submission, staff quotation preparation/sending, customer accept/decline, quote history.
- **bookings:** `Booking`/`BookingExtra`; public booking creation, session-bound success page, public tracking, staff status lifecycle, history-retention protections.
- **payments:** `Payment`; M-Pesa STK Push initiation, callback handling, independent STK Push Query verification, reconciliation command.
- **notifications:** `QuoteStatusNotification`; durable quote-status emails with attempt tracking and staff-authorized retry.
- **services:** `ServiceCategory`, `Service`, `ServiceFeature`, `ServiceFAQ`, `ExtraService`; public service list/detail.
- **staff:** `Staff`; availability, city coverage, conflict checks, assignment.
- **gallery:** `Gallery` (legacy before/after) and `GalleryPhoto` (public gallery with service/category filters and pagination).
- **website:** `HeroSection`, `HeroSlide`, `ProcessStep`; shared CMS content via `website_content` context processor.
- **core:** home/contact views, contact form/email, CMS section models (`WhyChoose*`, `CompanyStatistic`, `Testimonial*`, `FAQ*`), public rate-limit utility, `/health/` endpoint.

## Important data models and relationships

- `Customer` → `User` (OneToOne, nullable); `Customer` has bookings (`related_name="bookings"`) and quote requests (`related_name="quote_requests"`). Normalized email uniqueness via `customer_normalized_email_unique`.
- `PendingCustomerRegistration` → `User` (OneToOne) stores the phone captured at signup until verification.
- `QuoteRequest` → optional `Customer` and `Service`; stores estimate (`estimated_price`) separately from staff quotation (`proposed_amount`, `quote_valid_until`, `quote_sent_at`).
- `Booking` → `Customer` (PROTECT), optional `created_by` user, `Service` (SET_NULL), `Staff` (SET_NULL); `BookingExtra` → `Booking` (CASCADE) and `ExtraService` (PROTECT) with name/price snapshots.
- `Payment` → `Booking` (PROTECT); stores M-Pesa identifiers (`checkout_request_id`, `merchant_request_id`, `mpesa_receipt`), status, and verification scheduling/lease fields (`verification_attempt_count`, `last_verification_at`, `next_verification_at`, `verification_lease_id`, `verification_lease_expires_at`).
- `QuoteStatusNotification` → optional `QuoteRequest` (SET_NULL) plus `retrying_by` user; unique `event_key` prevents duplicate events.
- `Service` → `ServiceCategory` (SET_NULL); `ServiceFeature`/`ServiceFAQ` cascade from `Service`; `GalleryPhoto` → `Service` (PROTECT).
- `Staff` is standalone (role/city/availability) and referenced by `Booking.staff`.

## Business logic and service-layer conventions

- Multi-step writes use `@transaction.atomic` and `select_for_update` where concurrency matters (booking status, quote status, payment transitions, customer verification, notification claiming).
- Status changes go through explicit transition maps (`ALLOWED_STATUS_TRANSITIONS`) rather than direct assignment.
- Services raise `ValueError`/`ValidationError` for domain failures; views translate these into form errors or user messages.
- Provider/network calls are kept out of DB transactions where possible (e.g., payment initiation releases the booking lock before calling Safaricom).

## Customer registration, verification, authentication, and profile workflows

- `register_customer` creates an inactive `User` plus `PendingCustomerRegistration` via `create_pending_customer_registration`, then emails a verification link (`customer_verify`) built with `default_token_generator`.
- `verify_customer_email`/`verify_customer_account` activates the user, resolves or creates the `Customer` by normalized email, links the user, deletes the pending registration, and calls `link_guest_quote_requests` to attach matching guest quotes.
- `resend_verification` only emails when exactly one inactive pending registration matches; the response is intentionally non-enumerating.
- Login uses `CustomerAuthenticationForm` (email→username mapping); password reset uses Django's auth views with custom templates.
- `customer_profile`/`customer_dashboard`/`customer_quote_history` require login and a linked `Customer`; missing profiles show a support message.

## Guest and authenticated quote workflows

- `QuoteView.post` accepts guest or authenticated submissions, validates `QuoteRequestForm`, and calls `create_quote_request(data, user=request.user)`. Guests are stored with `customer=None`; authenticated users are linked to their `Customer`.
- `create_quote_request` persists customer/property/service details and a preliminary `estimated_price` from `calculate_quote`.
- Staff advance quotes through `change_quote_status`/`prepare_quotation`; `sent`/`declined`/`expired` transitions create `QuoteStatusNotification` records and deliver on commit.
- Customers accept/decline via `accept_customer_quote`/`decline_customer_quote` (login + POST), which call `accept_quote`/`decline_quote` and enforce ownership/status rules.

## Booking creation, ownership, lifecycle, tracking, and history retention

- `BookingCreateView.post` validates `BookingForm`, resolves the customer (`get_or_create_customer` for guests, `created_by` for authenticated users), calls `create_booking`, updates repeat-customer status, and stores `request.session["booking_success_id"]`.
- `create_booking` validates service/date/time/city/address, assigns staff via the staff service layer, snapshots extras, and computes `total_price`.
- `Booking.created_by` attributes authenticated bookings to the user (migration `0004_booking_created_by`).
- `change_booking_status` enforces `ALLOWED_STATUS_TRANSITIONS` under `select_for_update`; admin actions reuse it.
- `BookingSuccessView` and `initiate_booking_payment` only serve the session that created the booking (`booking_success_id`).
- `BookingTrackView` looks up by `CLX-######` reference plus customer email, with its own cache counters: 5 attempts per IP+reference and 30 per IP per 600 seconds.
- Retention: `Booking.customer` and `BookingExtra.extra_service` use `PROTECT`; `BookingExtra` snapshots `extra_service_name`/`extra_service_price` (migration `0005_preserve_booking_history_and_extra_snapshots`); admin blocks deletes and prevents moving/reassigning extras.

## Payment lifecycle and M-Pesa Daraja integration

- `Payment` statuses: `pending → initiating → processing → paid/failed`, plus `unknown` for ambiguous outcomes. Method is currently `mpesa` only.
- `initiate_booking_payment` is POST-only and session-bound; it blocks duplicate attempts for `paid`/`initiating`/`processing`/`unknown`, reuses `pending`, and creates a new record after `failed`. It re-checks `cancelled` inside `select_for_update` before creating/initiating.
- `initiate_payment` persists `initiating`, calls `MpesaIntegration.initiate_stk_push`, then marks `processing` or `unknown`/`failed` appropriately.
- `mpesa_callback` (`payments/mpesa/callback/`, CSRF-exempt POST) parses the Daraja payload and calls `process_mpesa_callback`, which uses the callback only as a trigger to run `verify_payment`.
- `verify_payment` performs an independent STK Push Query (`query_stk_push`) for `processing`/`unknown` payments, validates checkout/merchant IDs, and applies `mark_payment_paid`/`mark_payment_failed` under a short lock. All query paths share a DB-backed verification guard: atomic lease claim, cooldown via `next_verification_at`, bounded exponential backoff with jitter, and `Retry-After` handling for HTTP 429/5xx.
- `MpesaIntegration` reads `MPESA_CONSUMER_KEY`, `MPESA_CONSUMER_SECRET`, `MPESA_SHORTCODE`, `MPESA_PASSKEY`, `MPESA_CALLBACK_URL`, and `MPESA_ENVIRONMENT` (`sandbox`/`production`) and selects the Daraja base URL accordingly.
- `reconcile_mpesa_payments` (`python manage.py reconcile_mpesa_payments [--limit N] [--dry-run] [--payment-id ID] [--delay SECONDS]`) re-checks `processing`/`unknown` payments and pending callback metadata with a checkout ID; it respects the same verification cooldown/lease, reports skipped payments, and defaults to limit 100/max 500 with a 1-second provider-attempt delay.

## Quote-status notification delivery, persistence, and staff retry

- `change_quote_status` creates a `QuoteStatusNotification` snapshot (recipient, subject, text/html bodies, unique `event_key`) and schedules `deliver_quote_status_notification` on commit.
- Delivery claims `pending → sending` atomically, increments `attempt_count`, sends via `send_template_email`, and finalizes to `sent` or `failed` with `last_error`.
- `retry_quote_status_notification` requires an active staff user with `notifications.change_quotestatusnotification`; the admin action `retry_selected_notifications` exposes it.
- Known limitation: a process crash after claiming `sending` can leave a stale `sending` record; there is no automatic sweeper—recovery is manual.

## Public endpoint rate-limiting policies

Implemented in `apps_core/core/rate_limit.py` and applied to public POST handlers before validation/business logic. GET requests are not throttled; throttled requests return `errors/429.html` with HTTP 429. Identifiers are normalized (strip/lowercase) and cache keys use an HMAC digest; missing identifier fields skip only that scope while IP limits still apply; cache failures fail open.

| Endpoint | Scopes (limit/window) |
|---|---|
| Contact | IP 5/hour; IP+email 5/day |
| Quote | IP 10/hour; IP+email 5/day; user 20/day |
| Booking create | IP 10/hour; IP+email 5/day; user 10/day |
| Customer register | IP 5/hour; IP+email 3/day |
| Resend verification | IP 5/hour; IP+email 3/day |
| Login | IP 20/hour; IP+username 10/hour |
| Password reset | IP 5/hour; IP+email 3/day |
| Booking track (separate limiter) | 5 per IP+reference; 30 per IP; 600s window |

## Admin permissions and data-retention protections

- `BookingAdmin`/`BookingExtraAdmin`: no add/delete; status changes only via actions that call `change_booking_status`; extras cannot be moved/reassigned.
- `PaymentAdmin`: delete and bulk delete disabled.
- `QuoteRequestAdmin`: quotation preparation/status workflow; no add/delete.
- `QuoteStatusNotificationAdmin`: read-only delivery records; retry via staff-authorized action.
- `CustomerAdmin`: form rejects normalized-email duplicates.
- Gallery/services/staff/website admins exist but have lighter test coverage (see gaps).

## Security considerations

- Session-bound booking success/payment authorization; POST-only payment initiation; CSRF-exempt callback is signature-agnostic but only triggers independent verification.
- Public POST rate limiting with normalized identifiers and digest cache keys; booking tracking has its own throttling.
- Customer emails are normalized and uniquely constrained; verification/reset tokens use Django's `default_token_generator`.
- Admin delete protections preserve booking/payment/notification history; sensitive payment identifiers are excluded from customer-facing pages/tests.

## Deployment configuration and known limitations

- **Target architecture:** Render Django web service + Neon PostgreSQL + Cloudinary media. Build with `pip install -r requirements.txt && python manage.py collectstatic --no-input`; start with `gunicorn config.wsgi:application`; health check `/health/`.
- **Database:** `DATABASE_URL` is parsed for Neon/hosted PostgreSQL and preserves `sslmode`; local `DB_*` values remain the fallback. No data-destructive deployment step is required beyond normal `migrate`.
- **Static/media:** `STATIC_ROOT=staticfiles/` is collected at build time and served by WhiteNoise; uploaded media uses Cloudinary when configured, otherwise local `FileSystemStorage` (not durable on ephemeral hosting).
- **Security:** `DEBUG=False` requires `SECRET_KEY`, enables HTTPS redirect/cookie/HSTS settings through env-configurable values, trusts `X-Forwarded-Proto` for Render's proxy, and uses `CSRF_TRUSTED_ORIGINS` for HTTPS origins.
- **Logging:** console logging is configured for Django and `apps_core`; provider errors retain safe M-Pesa diagnostics without secrets or phone numbers.
- **Cache:** no `CACHES` setting is configured, so Django uses process-local `LocMemCache`. Rate-limit counters are not shared across workers/processes; production multi-worker deployments need a shared cache (Redis/Memcached) for consistent limiting. The limiter fails open if the cache is unavailable.
- **Email:** Render free web services block outbound SMTP ports 25/465/587; SMTP credentials may boot the app but cannot deliver mail on free Render. A paid Render instance or HTTPS email API/provider is a hosting decision, not implemented here.
- **M-Pesa reconciliation:** `reconcile_mpesa_payments` must be run manually or scheduled externally (for example a Render Cron Job); there is no built-in scheduler/task queue.
- **Notifications:** stale `sending` records after a crash require manual reconciliation.

## Development conventions and safeguards

- Backend-first: models/services before templates; keep business logic in `services.py`, not templates.
- Use Bootstrap 5 + custom CSS, mobile-first, reusable `{% include %}` components, template inheritance.
- Prefer class-based views where appropriate; function views for auth/account flows.
- Add comments only when necessary; avoid duplicate code; keep code readable.
- Preserve uncommitted work; do not stage/commit unless asked; run `git diff --check` after edits.
